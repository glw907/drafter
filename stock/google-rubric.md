# The Google rubric

The editor seat grades a page against the rules on this page. Each rule paraphrases one page of
the [Google developer documentation style guide](https://developers.google.com/style) and links
to it. The rules are short on purpose: when a rule leaves a case open, read the guide's page,
which governs. A finding names the rule by its heading.

## Address the reader as you

Write to the reader in the second person, with "you" and "your". Don't put the writer in the
task with "we", "our", or "let's". Use the third person only for what the software or an end user
does.

Source: [Second person and first person](https://developers.google.com/style/person)

## Give instructions in the imperative

Tell the reader what to do with a verb in the imperative, such as "Run", "Set", or "Open". The
"you" is implied.

Source: [Second person and first person](https://developers.google.com/style/person)

## Prefer active voice

Make the actor the subject of the sentence, so the reader knows who does what. Passive voice is
acceptable when the actor is unknown or doesn't matter to the reader.

Source: [Active voice](https://developers.google.com/style/voice)

## Use the present tense

Describe how a product behaves in the present tense. Use the future tense only for an action
that happens later, after some other event, and never to promise how a later release behaves.

Source: [Present tense](https://developers.google.com/style/tense)

## Put the condition before the instruction

When an instruction depends on a goal or a circumstance, state that first, so a reader can skip
an instruction that doesn't apply to them.

Source: [Sentence structure](https://developers.google.com/style/sentence-structure)

## Write procedures as numbered steps

A sequence of actions is a numbered list, one action per step. Introduce the procedure with a
complete sentence that gives context the heading doesn't, never a fragment that the steps
finish. A single step is one sentence, not a numbered list of one.

Source: [Procedures](https://developers.google.com/style/procedures)

## Use sentence case and task headings

Write headings in sentence case. Start a task heading with a bare verb, such as "Install the
tool", and give a concept heading a noun phrase. Don't skip heading levels.

Source: [Headings and titles](https://developers.google.com/style/headings)

## Introduce lists and keep their items parallel

Introduce a list with a complete sentence. Give every item in a list the same grammatical form.
Don't make a list of one item.

Source: [Lists](https://developers.google.com/style/lists)

## Put code in code font

Mark up anything the reader types or reads from code in code font: commands, flags, file names,
class names, and literal values. Don't use code font for product names or for a URL the reader
visits in a browser.

Source: [Code in text](https://developers.google.com/style/code-in-text)

## Make link text descriptive

Link text says what the reader finds at the target. Don't use "click here" or "this page" as link
text. Link selectively, since each link asks the reader to decide whether to leave.

Source: [Cross-references and linking](https://developers.google.com/style/link-text)

## Define abbreviations on first use

Spell out an abbreviation the first time it appears, with the short form after it, and then use
the short form. Leave out an abbreviation that the page's readers are unlikely to know.

Source: [Abbreviations](https://developers.google.com/style/abbreviations)

## Avoid jargon

Use plain words over the private terms of a group. When a page needs a term of art, define it on
first use or link to a definition.

Source: [Jargon](https://developers.google.com/style/jargon)

## Write timeless documentation

Describe the product as it is. Don't use words that date the page, such as "now", "new",
"currently", or "latest", and don't describe how a feature changed from an earlier version.

Source: [Timeless documentation](https://developers.google.com/style/timeless-documentation)

## Keep a conversational, direct tone

Sound like a knowledgeable colleague: friendly and respectful, neither stiff nor flippant. Don't
pad instructions with "please". Skip slang, jokes, and idioms that don't translate.

Source: [Voice and tone](https://developers.google.com/style/tone)

## Use common contractions

Use common two-word contractions, such as "don't" and "isn't", for a conversational tone. Don't
invent contractions or stack three words into one.

Source: [Contractions](https://developers.google.com/style/contractions)
